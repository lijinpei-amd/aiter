    * tile: regsiter/lds tile handled collectively by thread-block. `Tile` is a general concept, which could mean thread-block tile, warp tile, sliced sub-tile etc, in this code base, without furthur modification, tile means the `BLOCK_M * BLOCK_N * BLOCK_K` tile.
    * slot: sliced sub part of tile. For better performance, tile is sliced into `NUM_M_SLOTS * NUM_N_SLOTS` part, each is called a slot. A slot is `SLOT_M x SLOT_N`, so `NUM_M_SLOTS = BLOCK_M / SLOT_M` and `NUM_N_SLOTS = BLOCK_N / SLOT_N`.
    * non-K slot: an operand's share of a slot along its own non-K axis. Operand A is sliced along M only and B along N only, so A's copies and reads are indexed by an M slot and B's by an N slot. A slot `(mi, ni)` reads A's non-K slot `mi` and B's non-K slot `ni`.
    * step: one iteration of the pipelined K loop, which advances the tile by `BLOCK_K`. A step selects K tile `r` and issues the MFMAs of K tile `r - 1`.
    * component: `(operand, is_scale)`, one of an operand's payload and its scale. Each component has its own ring buffer, placement (LDS or registers) and copies.
    * ring buffer (ring): a component's `D` buffers (`num_buffers(operand, is_scale)`, `Schedule.ring_depth`), reused in rotation so the copies for later steps land while the current buffer is read. A buffer holds one value of the component: all its non-K slots for one step, or for a scale the `R` steps one scale slot spans, so a scale ring advances once every `R` steps. A value lives `L = (D - 1) * R + 1` steps (`live_span`) and is selected `F` steps after its copy is issued, counting both ends (`fill_span`): `F = L` through LDS, `F = L - 1` in registers, which skip the DS read. Step `s` selects buffer `(s // R) % D` and fills buffer `((s + F - 1) // R) % D`. The ring period, `lcm(D * R)` over the present components, is the number of steps until every ring is back at buffer 0.
        * LDS ring: `D` LDS allocations. Its index may be a runtime value.
        * register ring: one flat tuple of `D` buffers' fragments, buffer-major; a scale buffer holds `scale_fragments_per_buffer`, one fragment per non-K slot and K slot of each step it spans. A tuple has no runtime index, so the loop body is unrolled to a whole register ring period and the index is counted from the loop's first step; straight-line steps instead rotate the tuple (`_rotate_buffers`) so index 0 is always the current value.
    * scale slot: the part of an operand's scale that one copy fetches, `scale_slot_nonk x scale_slot_k`, set by `SCALE_SLOT_M` (A) or `SCALE_SLOT_N` (B) and `SCALE_SLOT_K`. K counts logical payload elements, not E8M0 bytes. Only a shuffled scale sets it independently of the payload: one scale slot spans `scale_slot_k / BLOCK_K` steps (the scale K-step ratio `R`) and `scale_slot_nonk / SLOT_M` (B: `/ SLOT_N`) non-K slots, and is copied once and selected once for all of them, at its first step and its first non-K slot. A zero knob takes the default, one non-K slot by `max(256, BLOCK_K)`, because a shuffle always packs K256. An unshuffled scale's scale slot is one non-K slot by `BLOCK_K`, the same as its payload's.
    * preshuffle: a component stored in HBM in an order other than row-major, so the kernel's copy and read match the MFMA instead of permuting at runtime. There are three, one flag each, but only two distinct byte orders because the two scale shuffles share one:
        * B payload, `B_PRESHUFFLED`: the 16x16 B payload preshuffle.
        * B scale, `B_SCALE_SHUFFLED` (`ScaleSwizzle.CDNA4_SCALE`), and A scale, `A_SCALE_SORTED_SHUFFLED` (`ScaleSwizzle.SORTED_SHUFFLED`): both the CDNA4 MX-scale order, differing only in which rows they hold and how they pad.
        * A payload is never preshuffled: its token rows are gathered per launch, so no fixed permutation exists.
        * Not a preshuffle: `WeightGuHbmLayout` (gate/up `INTERLEAVED` vs `SPLIT`) reorders B along N, but it is a separate layout choice, not one of the shuffle flags.
    * 16x16 B payload preshuffle: the HBM byte order of a preshuffled payload, 256 B tiles of 16 non-K rows by 16 B of K, ordered along K and then along rows. With `KB` the K extent in bytes, row `n` and K byte `k` land at `(n // 16) * (KB * 16) + (k // 16) * 256 + (n % 16) * 16 + k % 16`. A lane of a 16-wide MFMA reads 16 contiguous bytes of one row, so each read is one 16 B load and the 64 lanes of one load cover one contiguous 1024 B run. It is the order `aiter/ops/shuffle.py::shuffle_weight(w, (16, 16))` writes for every dtype, whose inner run is `16 // itemsize` elements. When `payload_byte_unit_lds_ok` holds, `byte_unit_lds_layout` keeps the same order in LDS, a 16-row unit with no padding, so the direct-to-LDS copy is one linear run and `ds_read_b128` is free of bank conflicts.
        * Gluon writes it with `_preshuffled_b` and reads it with `_blocked_b_hbm_offsets`, whose `run` is the elements in 16 B: 16 for 8-bit storage (fp8, packed fp4), 8 for bf16. Both are byte-identical to `shuffle_weight` for every storage width.
        * fp8 needs `k_width = 16`, the default `128 // storage_bits`. On the scaled 16x16x128 MFMA an fp8 lane holds two 16 B K runs, K `[16g, 16g + 16)` and `[64 + 16g, 64 + 16g + 16)` with `g = lane // 16`: `k_width = 16` describes exactly that, and each run is one 16 B load from the preshuffle. `k_width = 32`, one 32 B run per lane, puts values under the wrong E8M0 scale: measured on gfx950 with random scales, 0.58 relative error, against 4e-5 for `k_width = 16`. It looks correct only with unit scales, because any K order that A and B share gives the same dot product. fp4 is one contiguous 16 B run of 32 values per lane, also `k_width = 16` storage elements.
    * byte-unit LDS layout: `byte_unit_lds_layout`, the payload LDS order used where `payload_byte_unit_lds_ok` holds, otherwise Triton's `compute_efficient_padded_shared_layout`. It is defined in bytes, so one rule covers every storage width.
        * Preshuffled: the 16x16 B payload preshuffle kept as is, a unit of 16 rows by 16 B with no padding, so any K extent of whole 16 B runs keeps it.
        * Not preshuffled: a unit of 32 rows by 128 B of K (`LDS_UNIT_K_BYTES`), its rows in the order `1, 4, 16, 2, 8`, and 32 B of padding every 1024 B. One direct-to-LDS load, 64 lanes x 16 B, fills one padding interval with eight rows of 128 B.
        * `payload_byte_unit_lds_ok` needs each lane to read 16 B, `k_width * storage_bits == 128`, and the slot to hold whole units; without a preshuffle, also a 16-wide MFMA. Lane `l` then reads row `l % 16` at K byte `16 * (l // 16)`, and the next 64 B one read later on 8-bit 16x16x128 or one MFMA later on bf16 16x16x32: the same bytes either way. Simulated against Triton's `ds_read_b128` bank model (`test_moe_gemm_gluon_byte_unit_lds.py`), each 16-row tile of the 32-row unit reads conflict-free at any row offset, while a 32-wide MFMA reads it 2-way (lane rows 20-23 share banks with rows 0-3). The 16-row preshuffled unit is conflict-free for 16-wide and 32-wide reads.
        * 8-bit storage without a preshuffle also needs `tiles_per_warp >= 2` on the operand. It is measured, not a bank limit: at `tiles_per_warp` 1 the byte-unit B of a8w4 ran 0.8% (T=16) and 0.5% (T=64) slower cold, every round, though both layouts read conflict-free and copy whole 128 B lines (2026-10-17). a8w8 at T=16/64/256 was flat. bf16 takes the byte-unit layout at any `tiles_per_warp`, and was flat across all five token counts.
    * CDNA4 MX-scale order: the byte order of every shuffled E8M0 scale, laid out for the 16x16x128 scaled MFMA. With `r` a non-K row (M for A, N for B) and `k` a scale column (one byte per MX group of 32 payload K), the byte offset is `(r // 32) * K + (k // 8) * 256 + (k % 4) * 64 + (r % 16) * 4 + ((k % 8) // 4) * 2 + (r % 32) // 16`. Each 32-row stripe is one `K`-byte run of 256 B tiles, one tile per 8 scale columns. In a tile, MFMA lane `(k % 4) * 16 + r % 16` owns one dword whose four bytes are two K128 steps by two 16-row halves, so one dword holds the scales of four MFMAs (see packed scale). Only E8M0 scales with an MX group of 32 use it; a payload uses the 16x16 blocking. The same order is written by `aiter/ops/shuffle.py::shuffle_scale` (`e8m0_shuffle`), `aiter/ops/triton/utils/shuffle.py::_shuffle_scale_tile_gfx950(s, 32, 8)` and `csrc/include/mx_quant_utils.h::mx_scale_shuffle_idx`, and read by `_shuffled_scale_register_offsets` and `_shuffled_scale_stage_offsets`. The two scale flags match `e8m0_shuffle` byte for byte and differ only in their rows and padding:
        * `e8m0_shuffle`, the reference: the tensor's rows as given, padded to a multiple of 256 rows and 8 scale columns, so its stripe stride is the padded width.
        * `B_SCALE_SHUFFLED`: written offline by `_shuffled_b_scales` through `_shuffle_scale_tile_gfx950`. Per expert, its `N` rows in input order, gate and up halves kept separate. No padding: the host keeps raw scales unless `N` and `SLOT_N` are multiples of 32 and `K` of 256. It equals `e8m0_shuffle` of the `(E * N, K / 32)` scales, without the trailing padding.
        * `A_SCALE_SORTED_SHUFFLED`: written on every call by `moe_sort_scales.cuh` through `_sorted_shuffle_a_scales`. Rows in routing order, row `r` holding token `sorted_token_ids[r]`, each expert's rows padded to whole `BLOCK_M` blocks; a padding row repeats token 0's scale and a block past the last routed row is zero. It equals `e8m0_shuffle(a_scale[sorted_token_ids])`. Valid only when `KernelLayout.payload_a_sorted_shuffled_ok` holds and `K % 256 == 0`; a shape with no codegen instance of the C++ kernel falls back to raw scales.
        * Trap: `moe_sort_scales.cuh` also has a `BK == 128` branch that writes a different order, 4-column tiles with each dword's upper two bytes zero. Only `kBK = 256` in `mxfp4_moe_aux_dispatch.h` keeps it out of use.
    * storage/pack_divisor: for non sub-byte dtype(fp8, fp16, fp32),  storage dtype/shape is same as logical dtype/shape, and pack_divisor is 1; for fp4, two elements are packed into a int8 in k-dimension, therefore, logical refers to fp4 and its shape, storage refers to int8 and it shape, and pack_divisor is 2.
    * fragment: a component's values in registers, in a distributed layout. Unqualified, it is one slot's: one MFMA step's operand, or the accumulator. A scale slot fragment is a whole scale slot as one copy or read lands it, and the slot fragments are sliced out of it in registers. Layout and shape names say `fragment` for registers.
    * LDS view: a shared layout that reinterprets an LDS allocation as the tensor a read produces, naming each element's address. It is not the allocation's own layout and shape (`lds_layout`, `lds_shape`): a shuffled scale is allocated as a flat run in HBM byte order and read through a view in fragment order. A view and the fragment it is read into share a shape.
    * packed scale: a shuffled scale held as i32, each register one dword of four E8M0 bytes, handed whole to the matrix instruction, which picks each byte with a selector (`scale_packed_sel`). Only when the fragment keeps a dword's four bytes in one lane (`KernelLayout.scale_packed_ok`); otherwise the scale is u8. A packed scale is never u8 in registers, so it has no names of its own: the scale fragment shapes and layouts and the LDS view hold its i32 values; the LDS allocation stays u8.
