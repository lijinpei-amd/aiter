    * tile: regsiter/lds tile handled collectively by thread-block. `Tile` is a general concept, which could mean thread-block tile, warp tile, sliced sub-tile etc, in this code base, without furthur modification, tile means the `BLOCK_M * BLOCK_N * BLOCK_K` tile.
    * slot: an operand's share of the tile along its own non-K axis, `SLOT_M` rows of A or `SLOT_N` columns of B. Operand A is sliced along M only and B along N only, so A has `NUM_M_SLOTS = BLOCK_M / SLOT_M` slots, indexed by `mi`, and B has `NUM_N_SLOTS = BLOCK_N / SLOT_N`, indexed by `ni` (`KernelLayout.num_slots(operand)`). Copies and DS reads are per component slot (`CompSlot(component, index)`): each is issued at one pane of the step (`Schedule.buffer_load_pane`, `Schedule.ds_read_pane`, both keyed by a `CompSlot`), and `Schedule.buffer_load_slots` / `Schedule.ds_read_slot` give the inverse, the slot of each component a pane issues.
    * pane: the `SLOT_M x SLOT_N` part of the tile, `Pane(m_index, n_index)` or `(mi, ni)`, that A's slot `mi` and B's slot `ni` multiply into. The tile holds `NUM_M_SLOTS * NUM_N_SLOTS` panes, so a slot feeds every pane in its row (A) or column (B). Each pane has its own accumulator, and every step visits the panes in turn (the pane loop). `_frozen.py` predates these names: its slot is a pane and its non-K slot a slot.
        * pane index (`pane_index`): a pane's position in `[0, NUM_M_SLOTS * NUM_N_SLOTS)`, `ni * NUM_M_SLOTS + mi` (`Pane.linear_index(num_m_slots)`). It is at once the pane loop's visit order, the pane's accumulator index and the key of every per-pane schedule entry. A bare `pane` names the pane itself, a `Pane`, not this number.
    * step: one iteration of the pipelined K loop, which advances the tile by `BLOCK_K`. A step DS-reads K tile `r` and issues the MFMAs of K tile `r - 1`.
    * component: `Component(operand_index, is_scale)`, one of an operand's payload and its scale. `_types.py` names the four `A_PAYLOAD`, `A_SCALE`, `B_PAYLOAD`, `B_SCALE`; they compare and hash by value. `_frozen.py` keeps them as `(operand, is_scale)` tuples. Each component has its own ring buffer, placement (LDS or registers) and copies.
        * component index (`component_index`): a component's position in `COMPONENTS = (A_PAYLOAD, A_SCALE, B_PAYLOAD, B_SCALE)`, in `[0, 4)` (`Component.index()`). Per-component schedule tuples are indexed by it.
    * ring buffer (ring): a component's `D` buffers (`num_buffers(operand, is_scale)`, `Schedule.num_buffers`), reused in rotation so the copies for later steps land while the current buffer is read. A buffer holds one value of the component: all its slots for one step, or for a scale the `R` steps one scale slot spans (`Schedule.steps_per_buffer`), so a scale ring advances once every `R` steps. How long a value lives (`L`) and how many steps after its copy its MFMAs issue (`F`) are defined in PIPELINE.md. The buffer period (`Schedule.buffer_period`), `lcm(D * R)` over the present components (`Schedule.component_present`), is the number of steps until every ring is back at buffer 0.
        * LDS ring: `D` LDS allocations. Its index may be a runtime value.
        * register ring: one flat tuple of `D` buffers' fragments, buffer-major; a scale buffer holds one fragment per slot and K slot of each of the `R` steps it spans, `num_slots * num_k_slots * R`. A tuple has no runtime index, so the loop body is unrolled to a whole register buffer period (`Schedule.reg_buffer_period`) and the index is counted from the loop's first step; straight-line steps instead rotate the tuple (`_rotate_buffers`) so index 0 is always the current value.
    * DS read: taking a component's value out of its ring into the fragments that later steps' MFMAs consume. Each slot is DS-read in one pane (`Schedule.ds_read_pane`), by default the pane that copies its operand's payload, and in one of that pane's two regions (`Schedule.ds_read_in_mfma`): a pane runs its memory region, DS reads then fills, before its MFMA region, MFMAs then the remaining DS reads. From an LDS ring it is a `ds_read` into registers, after the pane's async wait. A register ring issues no DS read: its DS-read pane only places a tuple index, which matters only when `F = 1` (PIPELINE.md), where the same step's fill overwrites that tuple position. The DS read is then placed no earlier than the buffer-load pane, and in the MFMA region when it shares that pane, whatever `DS_READ_*_IN_MFMA` says, so it follows the buffer load; `Schedule.__init__` asserts that order. A step DS-reads a new value of a component every step for a payload and every `R` steps for a scale (`Schedule.ds_reads`); `Schedule.ds_read_slot` names the slot of each component a pane DS-reads.
    * scale slot: the part of an operand's scale that one copy fetches, `scale_slot_nonk x scale_slot_k`, set by `SCALE_SLOT_M` (A) or `SCALE_SLOT_N` (B) and `SCALE_SLOT_K`. Every scale K, the knob included, counts scale columns, one E8M0 byte per MX group of 32 payload K; a step's is `scale_block_k = BLOCK_K / 32`. Only a shuffled scale sets it independently of the payload: one scale slot spans `scale_slot_k / scale_block_k` steps (the scale K-step ratio `R`) and `scale_slot_nonk / SLOT_M` (B: `/ SLOT_N`) slots (the scale non-K slot ratio `Q`) (`KernelLayout.scale_slot_span[operand]`, the pair `(Q, R)`), and is copied once and DS-read once for all of them, at its first step and its first slot. A zero knob takes the default, one slot by `max(8, scale_block_k)`, because a shuffle always packs K256, 8 scale columns. An unshuffled scale's scale slot is one slot by `scale_block_k`, the same K as its payload's. A scale slot has two shapes over the same bytes. It is read and held (`scale_slot_shape_fragment`, through `scale_slot_lds_view_layout` into `scale_slot_fragment_layout`) in its logical shape as u8, or in its storage shape as i32 when packed:
        * logical, `scale_slot_shape_logical`: `[scale_slot_nonk, scale_slot_k]`, one E8M0 byte per element.
        * storage, `scale_slot_shape_storage`: the u8 shape it is copied and allocated in, one row per `U` non-K rows: `[scale_slot_nonk / U, U * scale_slot_k]`. A scale unit, `scale_unit_nonk x scale_unit_k` (`U` rows by scale columns), is what a scale stores contiguously and a scale slot holds whole. A shuffled scale's is 32 rows by 8 columns (K256), one 256 B tile in CDNA4 MX-scale order (`_packed_scale.UNIT_NONK x UNIT_K`), so a storage row is a 32-row stripe, its storage is `[scale_slot_nonk / 32, 32 * scale_slot_k]` and its default `scale_slot_k` is `max(8, scale_block_k)`. An unshuffled scale's is 1 by 1: it is row-major, so its storage shape is its logical shape. A packed scale slot is read and held in storage order as i32, `[scale_slot_nonk / 32, 32 * scale_slot_k / 4]`.
    * preshuffle: a component stored in HBM in an order other than row-major, so the kernel's copy and read match the MFMA instead of permuting at runtime. There are three, one flag each, but only two distinct byte orders because the two scale shuffles share one:
        * B payload, `B_PRESHUFFLED`: the 16x16 B payload preshuffle.
        * B scale, `B_SCALE_SHUFFLED` (`ScaleSwizzle.CDNA4_SCALE`), and A scale, `A_SCALE_SORTED_SHUFFLED` (`ScaleSwizzle.SORTED_SHUFFLED`): both the CDNA4 MX-scale order, differing only in which rows they hold and how they pad.
        * A payload is never preshuffled: its token rows are gathered per launch, so no fixed permutation exists.
        * Not a preshuffle: `WeightGuHbmLayout` (gate/up `INTERLEAVED` vs `SPLIT`) reorders B along N, but it is a separate layout choice, not one of the shuffle flags.
    * 16x16 B payload preshuffle: the HBM byte order of a preshuffled payload, 256 B tiles of 16 non-K rows by 16 B of K, ordered along K and then along rows. With `KB` the K extent in bytes, row `n` and K byte `k` land at `(n // 16) * (KB * 16) + (k // 16) * 256 + (n % 16) * 16 + k % 16`. A lane of a 16-wide MFMA reads 16 contiguous bytes of one row, so each read is one 16 B load and the 64 lanes of one load cover one contiguous 1024 B run. It is the order `aiter/ops/shuffle.py::shuffle_weight(w, (16, 16))` writes for every dtype, whose inner run is `16 // itemsize` elements. When `payload_byte_unit_lds_ok` holds, `byte_unit_lds_layout` keeps the same order in LDS, a 16-row unit with no padding, so the direct-to-LDS copy is one linear run and `ds_read_b128` is free of bank conflicts.
        * Gluon writes it with `_preshuffled_b` and reads it with `_blocked_b_hbm_offsets`, whose `run` is the elements in 16 B: 16 for 8-bit storage (fp8, packed fp4), 8 for bf16. Both are byte-identical to `shuffle_weight` for every storage width.
        * fp8 needs `k_width = 16`, the default `128 // storage_bits`. On the scaled 16x16x128 MFMA an fp8 lane holds two 16 B K runs, K `[16g, 16g + 16)` and `[64 + 16g, 64 + 16g + 16)` with `g = lane // 16`: `k_width = 16` describes exactly that, and each run is one 16 B load from the preshuffle. `k_width = 32`, one 32 B run per lane, puts values under the wrong E8M0 scale: measured on gfx950 with random scales, 0.58 relative error, against 4e-5 for `k_width = 16`. It looks correct only with unit scales, because any K order that A and B share gives the same dot product. fp4 is one contiguous 16 B run of 32 values per lane, also `k_width = 16` storage elements.
    * byte-unit LDS layout: `byte_unit_lds_layout`, the payload LDS order used where `payload_byte_unit_lds_ok` holds, otherwise Triton's `compute_efficient_padded_shared_layout`. It is defined in bytes, so one rule covers every storage width.
        * Preshuffled: the 16x16 B payload preshuffle kept as is, a unit of 16 rows by 16 B with no padding, so any K extent of whole 16 B runs keeps it.
        * Not preshuffled: a unit of 32 rows by 128 B of K (`LDS_UNIT_K_BYTES`), its rows in the order `1, 4, 16, 2, 8`, and 32 B of padding every 1024 B. One direct-to-LDS load, 64 lanes x 16 B, fills one padding interval with eight rows of 128 B.
        * `payload_byte_unit_lds_ok` needs each lane to read 16 B, `k_width * storage_bits == 128`, and the slot to hold whole units; without a preshuffle, also a 16-wide MFMA. Lane `l` then reads row `l % 16` at K byte `16 * (l // 16)`, and the next 64 B one read later on 8-bit 16x16x128 or one MFMA later on bf16 16x16x32: the same bytes either way. Simulated against Triton's `ds_read_b128` bank model (`test_moe_gemm_gluon_byte_unit_lds.py`), each 16-row tile of the 32-row unit reads conflict-free at any row offset, while a 32-wide MFMA reads it 2-way (lane rows 20-23 share banks with rows 0-3). The 16-row preshuffled unit is conflict-free for 16-wide and 32-wide reads.
        * 8-bit storage without a preshuffle also needs `tiles_per_warp >= 2` on the operand. This is a proxy that keeps one measured regression out, not a bank limit or a property of `tiles_per_warp`. With it dropped, the a8w4 harness pin (BLOCK_K 512, fp4 B, `tiles_per_warp` (1, 1)) ran 0.6-0.9% slower at T=16/64 in every round, from two causes that add up (2026-10-17):
            * AGPR spill, about half. Triton's layout already fills all 256 AGPRs there. The byte-unit B `ds_read` base address takes about 17 ops instead of 3, and holding it costs 56 VGPR spills: 16 extra AGPR copies in the loop and 8 values carried across the back-edge. The loop IR is otherwise identical, and swapping only that expression moves the spill.
            * B copy order, the rest. The same instructions with only the byte-unit copy offsets cost 0.1-0.5%, with identical L2 and EA request counts, so the cost is request order or DRAM locality, not traffic.
            * a8w8 with the same B layouts was flat at T=16/64/256. Its BLOCK_K 256 leaves room in registers, and its B rows sit 7168 B apart rather than 3584 B. bf16 takes the byte-unit layout at any `tiles_per_warp` and was flat across all five token counts. A cheaper byte-unit read-base expression would remove the spill half; one regressing config is too little data for a narrower rule.
    * CDNA4 MX-scale order: the byte order of every shuffled E8M0 scale, laid out for the 16x16x128 scaled MFMA. With `r` a non-K row (M for A, N for B) and `k` a scale column (one byte per MX group of 32 payload K), the byte offset is `(r // 32) * K + (k // 8) * 256 + (k % 4) * 64 + (r % 16) * 4 + ((k % 8) // 4) * 2 + (r % 32) // 16`. Each 32-row stripe is one `K`-byte run of 256 B tiles, one tile per 8 scale columns. In a tile, MFMA lane `(k % 4) * 16 + r % 16` owns one dword whose four bytes are two K128 steps by two 16-row halves, so one dword holds the scales of four MFMAs (see packed scale). Only E8M0 scales with an MX group of 32 use it; a payload uses the 16x16 blocking. The same order is written by `aiter/ops/shuffle.py::shuffle_scale` (`e8m0_shuffle`), `aiter/ops/triton/utils/shuffle.py::_shuffle_scale_tile_gfx950(s, 32, 8)` and `csrc/include/mx_quant_utils.h::mx_scale_shuffle_idx`, and read by `_shuffled_scale_register_offsets` and `_shuffled_scale_stage_offsets`. The two scale flags match `e8m0_shuffle` byte for byte and differ only in their rows and padding:
        * `e8m0_shuffle`, the reference: the tensor's rows as given, padded to a multiple of 256 rows and 8 scale columns, so its stripe stride is the padded width.
        * `B_SCALE_SHUFFLED`: written offline by `_shuffled_b_scales` through `_shuffle_scale_tile_gfx950`. Per expert, its `N` rows in input order, gate and up halves kept separate. No padding: the host keeps raw scales unless `N` and `SLOT_N` are multiples of 32 and `K` of 256. It equals `e8m0_shuffle` of the `(E * N, K / 32)` scales, without the trailing padding.
        * `A_SCALE_SORTED_SHUFFLED`: written on every call by `moe_sort_scales.cuh` through `_sorted_shuffle_a_scales`. Rows in routing order, row `r` holding token `sorted_token_ids[r]`, each expert's rows padded to whole `BLOCK_M` blocks; a padding row repeats token 0's scale and a block past the last routed row is zero. It equals `e8m0_shuffle(a_scale[sorted_token_ids])`. Valid only when `KernelLayout.payload_a_sorted_shuffled_ok` holds and `K % 256 == 0`; a shape with no codegen instance of the C++ kernel falls back to raw scales.
        * Trap: `moe_sort_scales.cuh` also has a `BK == 128` branch that writes a different order, 4-column tiles with each dword's upper two bytes zero. Only `kBK = 256` in `mxfp4_moe_aux_dispatch.h` keeps it out of use.
    * storage/pack_divisor: for non sub-byte dtype(fp8, fp16, fp32),  storage dtype/shape is same as logical dtype/shape, and pack_divisor is 1; for fp4, two elements are packed into a int8 in k-dimension, therefore, logical refers to fp4 and its shape, storage refers to int8 and it shape, and pack_divisor is 2.
    * fragment: a component's values in registers, in a distributed layout. Unqualified, it is one slot's operand for one MFMA step, or one pane's accumulator. A scale slot fragment is a whole scale slot as one copy or read lands it, and the slot fragments are sliced out of it in registers. The slot fragment that feeds one `dot_scaled` is `scale_fragment_shape_slot` / `scale_fragment_layout_slot`, packed or not. Layout and shape names say `fragment` for registers.
    * LDS view: a shared layout that reinterprets an LDS allocation as the tensor a read produces, naming each element's address. It is not the allocation's own layout and shape (`lds_layout`, `lds_shape`): a shuffled scale is allocated as a flat run in HBM byte order and read through a view in fragment order. A view and the fragment it is read into share a shape.
    * packed scale: a shuffled scale held as i32, each register one dword of four E8M0 bytes, handed whole to the matrix instruction, which picks each byte with a selector (`scale_packed_sel`). Its layout is `_packed_scale.packed_scale_layout`: shape `[nonk // 32, 32 * k // 4]` with `k` in scale columns, one row per 32-row stripe in HBM order, lane `l` holding dword `l` of every 32-row by K256 unit, register and warp bases stepping whole units; the dot takes a row-major reshape of it to the shape `mfma_scaled_packed` checks (`packed_scale_dot_layout`). An operand packs (`KernelLayout.scale_packed_ok`) when that layout exists, i.e. the two bases inside a dword (`[16, 0]`, `[0, 4]`) are register bases, and `packed_scale_sel` finds a selector list for each K phase. Triton reads register `i // len(sel)` for instruction `i`, so the instructions one dword serves must be consecutive: a K512 dot, whose consecutive instructions alternate K units, stays u8. Otherwise the scale is u8. A packed scale is never u8 in registers, so it has no names of its own: the scale slot is read and held in its storage shape as i32, and its slot fragments are `scale_fragment_shape_slot` / `scale_fragment_layout_slot`; the LDS allocation stays u8.
